## 1. Verdict

| | Score | Note |
| --- | --- | --- |
| **Code quality** | 8 / 10 | Genuinely senior work — comments explain *why*, reduced-motion is handled per component, technical claims are traceable to source records |
| **Release readiness** | 4 / 10 | Held back almost entirely by two unfilled config strings, not by the code |

The gap between those two numbers is the headline. This is a well-built site that
cannot be sent to a recruiter yet, and the blockers cost about two minutes to
fix. See **F01** and **F02**.

> **2026-10-07:** F01 is fixed; F02 still waits on a domain.
> [F39](#f39) (vulnerable `next`) was found and fixed the same day.

### Method

Static analysis of the full `src/` tree, the compiled `.next` output, and the
project's own source-of-truth document (`FORM UPDATE KOMPETENSI & PENGALAMAN
PROJECT.md`). Contrast ratios were computed from the actual stylesheet tokens
rather than eyeballed. The production server was started and the page, image
optimiser, font delivery and sitemap were exercised over HTTP.

**No browser was driven.** Everything in [§5](#5-not-verified) rests on reasoning
or on inspection of build output, not on observed rendering.

## 3. Open findings

### F01 — moved to [§4d](#4d-remediated-on-2026-10-07)

*Original finding, kept for the reasoning; the fix is recorded in §4d.*

**🔴 P0 — `site.github` is a placeholder.** `src/lib/content.ts:38` holds
`github: "[YOUR GITHUB]"`, rendered by `Contact.tsx` as
`<a href="[YOUR GITHUB]">`. That is a *relative* URL, so clicking it navigates to
`https://<your-domain>/[YOUR GITHUB]` and 404s — in the one section a recruiter
is most likely to interact with.

### F02
**🔴 P0 — `site.url` is a placeholder.** `src/lib/content.ts:40` holds
`https://your-domain.com`, consumed in five places: `layout.tsx` `metadataBase`,
`openGraph.url`, `alternates.canonical`, the JSON-LD `Person.url`, and
`sitemap.ts`.

This is active damage rather than an unfilled blank:

- The **canonical tag** tells Google the authoritative copy of this page lives on
  a domain someone else owns. That is a de-indexing risk for the real site.
- The **OG image** resolves to `https://your-domain.com/og.png`, so link previews
  on WhatsApp, LinkedIn and Twitter are broken — even though `public/og.png`
  itself is correct (verified 1200×630, 100 KB).

Still present in the shipped HTML as of this audit.

### F13 — moved to [§4d](#4d-remediated-on-2026-10-07)

*Original finding, kept for the reasoning; the fix is recorded in §4d.*

**🟡 P2 — Marquee contradicts itself.** `Marquee.tsx:69` sets
`aria-hidden="true"`, while the comment at lines 24–25 justifies keeping it
animating under reduced motion because it *"displays useful content (tech stack),

not use content as its justification for moving; if content, it should not be

### F18 — moved to [§4c](#4c-also-remediated-on-2026-07-27)

*Original finding, kept for the reasoning; the fix is recorded in §4c.*

**🟠 P1 — 3 high advisories in production dependencies.** Re-checked 2026-07-27,
and the picture is worse than this finding originally recorded. It described the
three as "`postcss`, `sharp` via `next`" — transitive tooling. `npm audit
--omit=dev` now lists **`next` itself** as the first vulnerable package, carrying
eight advisories of its own:

| Advisory | Reachable on this site? |
| --- | --- |
| DoS in App Router via Server Actions | No — no Server Actions |
| SSRF in Server Actions on custom servers | No — no custom server |
| Cache confusion of response bodies (×2) | No — every route is static |
| Unbounded Server Action payload (Edge) | No |
| SSRF in rewrites via attacker-controlled destination | No — no rewrites |
| **DoS in the Image Optimization API using SVGs** | **Possibly** — depends on the host |
| Unauthenticated disclosure of internal Server Function endpoints | No |

All three routes build as `○ Static`, and the project uses no Server Actions,
rewrites or custom server, so seven of the eight are unreachable by construction.
The image optimiser is the exception: it is used for the profile photo, and
whether the endpoint is live depends on the deployment target.

**The severity was raised from P3 to P1 not because exposure changed, but because
the fix turned out to be cheap and the original entry made it sound expensive.**
"Outside the currently pinned range" is accurate but misleading: the pin is an
exact version (`"next": "15.5.19"`), so `15.5.22` is a **patch** bump inside
15.5.x, not a major. Recorded as a task in
[`HANDOVER.md`](./HANDOVER.md#next-up).

Dev-tree advisories added by the ESLint chain were assessed separately and
deliberately accepted — rationale in
[`DECISIONS.md` → D10](./DECISIONS.md#d10--brace-expansion-advisory-not-overridden).

### F28 — moved to [§4c](#4c-also-remediated-on-2026-07-27)

*Original finding, kept for the reasoning; the fix is recorded in §4c.*

**🔵 P3 — `framer-motion` was carried for a single component.** One import site in

### F29
**🔵 P3 — Tailwind v4 is installed; one utility class is used.** The only
Tailwind utility anywhere in `src/` is `object-cover` (`Work.tsx:154`). The
design system is hand-written CSS built on custom properties in `globals.css`.

**Assessed and accepted, not a defect.** For a design this bespoke — heavy
animation, one-off layouts, a token-driven two-theme palette — utility classes
would add little, and the custom-property approach is what makes the theme toggle
a single attribute flip. Tailwind is effectively paying for its CSS reset and the
option to use utilities later.

Recorded so the trade-off is a decision rather than an accident. Removing it
would mean replacing the reset by hand and re-verifying the whole stylesheet;
that is not obviously worth it.

### F40
**🟡 P2 — The photo badge fails contrast in the light theme.** Found by the
2026-10-08 browser run ([HANDOVER → Browser test](./HANDOVER.md#browser-test--2026-10-08)).
`.photo-badge` (`globals.css:308`) sets `background: rgba(10,10,11,0.6)`, a
fixed dark overlay, and `color: var(--text)`, which follows the theme. In the
light theme the computed pair is `rgb(17,17,16)` on near-black, about 1:1, so
the "Bogor, West Java, Indonesia" label over the photo cannot be read.

This also corrects [F09](#f09) and [D03](./DECISIONS.md#d03--contrast-tokens-are-tuned-against-two-backgrounds-not-one):
those checked the ten token pairs, but this element pairs a token with a
hard-coded colour, so it was never in the set. "All colour pairs clear AA" was
true of the tokens, not of the page.

**Fix:** give the badge a fixed light text colour, since its background is
always dark, or a light-theme background. Re-check the ratio after.

## 4. Remediated in this pass

Each entry states the defect, the fix, and the evidence it works.

### F03
**Skill legend filled 4/5 dots for every level.** All three legend groups —
Expert, Working, Learning — rendered four filled dots out of five. The legend
teaching the reader how to interpret the dots was itself wrong, and its labels
did not match the five-level scale documented in `content.ts`.

Fixed by making the legend data-driven: `skillScale` in `content.ts` is now the
single source of truth, rendered by one `Dots` component shared between the
legend and the skill pills, so the two can no longer disagree. Verified in built
HTML:

```
Learning 1/5 · Basic 2/5 · Working 3/5 · Proficient 4/5 · Expert 5/5
```

### F04
**Hydration mismatch on every repeat visit.** `Loader.tsx` read `sessionStorage`
inside a `useState` initialiser. The server rendered the loader markup (confirmed
present in `.next/server/app/index.html`); the client's first render returned
`null`. React 19 reports a mismatch and discards the subtree — on precisely the
visit that should have been fastest.

Fixed by adopting the pre-paint pattern the project already used for theming: a
shared flag module (`lib/intro.ts`), an inline script stamping
`html[data-intro="played"]` before first paint, and CSS that hides the loader.
The component now renders identical markup on server and client and unmounts from
an effect. See [D01](./DECISIONS.md#d01--the-loader-renders-on-the-server-and-is-hidden-by-css).

### F05
**Page permanently covered without JS.** `.loader` (z-index 200) and `.wipe`
(z-index 199) ship in the static HTML and were removed only by React. With no JS
the visitor saw a frozen loading screen reading `00` forever, with the entire
server-rendered page sitting underneath it.

Fixed in two layers, because one does not cover both failure modes —
see [D02](./DECISIONS.md#d02--two-layer-no-js-fallback). The `<noscript>` block
additionally hides the burger and theme toggle (dead controls without JS) and
restores the plain inline links, so mobile is not left with zero navigation.

### F07
**`lenis.css` never imported.** Low impact on its own, but it became a
prerequisite for F10: `lenis.stop()` relies on `.lenis-stopped { overflow: clip }`
from that stylesheet to actually hold the page still. Now imported in
`Providers.tsx`.

### F09
**Four colour tokens below WCAG AA.** All were used on 11–14px text. Values were
re-derived by holding hue and saturation and moving lightness only, testing
against **both** `--bg` and `--bg-2` — the second surface was the hidden
constraint that made the original values fail.

| Token | Before | After | After (bg / bg-2) |
| --- | --- | --- | --- |
| dark `--text-3` | `#76756d` | `#7e7d74` | 4.78 / 4.63 |
| light `--text-3` | `#6f6e66` | `#67675f` | 4.96 / 4.61 |
| light `--accent` | `#5d7c00` | `#546f00` | 5.00 / 4.65 |

An unplanned gain: `--accent` also serves as a *fill* behind `--accent-ink`
(`.btn.primary`, `.skip-link`, `::selection`). That pair rose from **4.20 → 4.94:1**.

All 10 foreground/background pairs now clear AA, verified by parsing the shipped
stylesheet. The README's claim of AA contrast in light mode — previously false —
is now accurate.

### F10
**No navigation below 760px.** `globals.css` hid all four nav links via
`.nav-links a:not(.icon-only)`, and no hamburger existed anywhere in the
codebase. The `.icon-only` class sits on the theme-toggle `<button>`, not on any
`<a>`, so the `:not()` excluded nothing. Mobile visitors — the majority for a
link shared with a recruiter — had to scroll manually through six sections.

`Nav.tsx` was rewritten with a 44×44 trigger (WCAG 2.5.5), a `role="dialog"
aria-modal` panel, focus moved in and trapped in both directions, Escape to
close, focus restored to the trigger, automatic close when the viewport crosses
the breakpoint, and scroll lock through `lenis.stop()`. The icon is driven
directly by `[aria-expanded="true"]`, so what is displayed cannot diverge from
what assistive technology is told.

Two issues found during self-review and fixed: the dialog needed its own close
control (`aria-modal` hides the outside burger from assistive tech), and
`justify-content: safe center` prevents the menu clipping on short landscape
screens.

### F12
**Levels announced without their scale.** Pills carried
`aria-label="level 2 of 5"` while the legend explaining the scale was
`aria-hidden`. Screen-reader users heard a number with no way to learn what it
meant. Labels now name the level directly — verified in built HTML:

```
aria-label="PHP — Expert"    aria-label="Python — Basic"    aria-label="SQL — Proficient"
```

### F14
**Raw eager `<img>` for the profile photo.** 121 KB JPEG, no AVIF/WebP, no
srcset, no lazy loading. Converted to `next/image` with a static import.

Measured against the running production server: **121 KB eager JPEG →
44.8 KB lazy WebP** (HTTP 200, `content-type: image/webp`), plus a generated blur
placeholder and 16 srcset candidates.

### F15
**Render-blocking fonts from two third-party origins.** `layout.tsx` loaded
stylesheets from `api.fontshare.com` and `fonts.googleapis.com` — two extra DNS +
TLS handshakes before any text could paint, visitor IP and user-agent disclosed
to two third parties, and no possibility of a strict `style-src` CSP.

All three families are now self-hosted through `next/font`, carrying only the
weights the stylesheet actually uses (8 requested → 5 shipped, 88 KB total).
